Cell Map v1 — a 3-D obstacle map cuMotion can plan against

MoveIt's planning scene is empty and cuMotion knows only a ground plane, so every "collision-free" plan in this cell is collision-free by ignorance. This page records how we gave the planner a real world: the wrist D435i, freedriven around the cell, fused by nvblox into a 2 cm ESDF directly in base_link, saved once and loaded by an opt-in planner. Built 2026-08-26.
pipeline built & bench-rehearsed end to end box detour +3.5 cm vs Pilz −11 cm (synthetic) design change: camera stays on the arm, no SLAM calibration + live scan: captain steps, in progress

1The defect this fixes

Three planners run in this cell and none of them knows the shelf exists. OMPL, Pilz and CHOMP plan against an empty scene; cuMotion is the only one with any world at all, and that world is a single ground plane (RUNBOOK §8b/8c). The approach demo works around this with a hand-maintained whitelist of collision boxes — which protects only against the obstacles somebody remembered to type in.

before

Empty scene

A straight-line plan between two poses goes straight through whatever is between them. Bench-measured on a synthetic 20 cm cube: Pilz PTP drives the arm 11 cm inside the obstacle and reports success.

after

ESDF world

cuMotion reads an nvblox ESDF built from what the camera actually saw. Same two poses, same cube: the plan arcs over it with 3.5 cm clearance at the closest collision sphere, and straightens again once the cube is removed and re-scanned.

2The design change that made this tractable

The original design (firstmate's cell-map-slam.html, 2026-08-26 rev 2) had the captain carry the camera and recover its pose with cuVSLAM, then register the SLAM map to the robot through an AprilTag. The captain changed the plan the same day: the camera stays strapped to the tool flange and the arm is freedriven by hand. That deletes an entire error source and an entire subsystem.

ConcernHandheld + cuVSLAMCamera on the arm (chosen)
Camera pose Visual odometry — drifts, can lose tracking on plain walls, needs a loop-closure check Forward kinematics — sub-mm, drift-free, always available
Registration to the robot AprilTag anchor base_link → map, must be up before integration starts; tag error enters every voxel None. Depth is integrated in base_link natively
Remaining unknown VSLAM drift and the mount transform The mount transform only — so calibrating it becomes step 1
Missing packages realsense_splitter absent; firmware 5.12.8.200 may not emit the metadata the stereo-IR mode needs Nothing missing — segmenter and nvblox are both in the image
Coverage The whole room, including space the arm can never enter The reach envelope — which is exactly the volume collision avoidance is about

3Pipeline and frame chain

There is no map or odom frame anywhere in this system. The camera's pose is read out of the robot, and the only transform that is not measured by the robot itself is the one bolted between the flange and the lens.

/joint_states ──► base_link ──► tool0 ──► camera_link ──► camera_color_optical_frame (UR driver) ▲ │ │ ▼ calib/tool0_to_camera_<date>.yaml depth + colour ── hand-eye, AX = XB ── │ ▼ /joint_states ──► robot segmenter ──► masked depth │ ▼ nvblox (2 cm TSDF/ESDF, global_frame base_link) │ save_map ──► cumotion/maps/cell-<date>.nvblx │ load_map ──► cuMotion read_esdf_world:=true

why a segmenter

The arm must not map itself

The wrist camera sees the forearm from very close, where the XRDF spheres are a coarse model — and the strapped camera and its cable are not in the model at all. Unmasked, the arm becomes a permanent obstacle and every plan starts in collision. The masked halo stays unobserved, which cuMotion treats as free, so the mask costs nothing: bench-verified by planning successfully out of a park pose whose region was never observed.

why calibration is a gate, not an option

4° at 1 m is 7 cm

The mount transform currently in wrist_rig.launch.py is a documented guess (±5 cm, 4.2° residual). A map built on it is worse than no map: it would clear paths that hit real shelves, with the planner's confidence attached. So run_scan.sh refuses to start without a calibration file. Target < 5 mm / 1°, independently validated against a second tag at < 10 mm / 1°.

4Bench rehearsal — the whole pipeline, before touching the arm

The captain's physical time is expensive and hard to repeat, so the entire chain was rehearsed first on synthetic depth (tools/fake_depth.py renders a table plane, a shelf slab at y 1.4 and a 20 cm cube, and publishes the camera TF directly). The real nvblox, real segmenter, real cuMotion and real save/load did all the rest. The arm never moved.

5Three defects the bench found before the captain could hit them

Each of these would have burned a physical session. All three are now designed out, and the reasoning is recorded so the next person does not undo them.

  • A planner that looks alive and refuses everything. cuMotion with read_esdf_world:=true blocks forever if the ESDF service is absent, and answers World update failed to every request if nvblox is up but empty. planner.launch.py therefore starts cuMotion only after map_ctl.py load exits 0, and shuts down loudly otherwise — so nothing can ever block on the ESDF service with no map.
  • A 0.04 m buffer that breaks every start state. Widening the world buffer uniformly puts the upper arm's root sphere (r 0.09, sitting 3.8 cm above the mounting plane) inside cuMotion's ground plane, and every plan fails with INVALID_INITIAL_CSPACE_POSITION. ur10_map.xrdf widens forearm/wrist_1/2/3/tool0 to 0.04 and keeps shoulder/upper_arm at 0.02 — those links never leave the base region anyway.
  • Joint goals that are already in collision. A goal pre-solved by MoveIt's /compute_ik against an empty scene can put the forearm 1–9 cm inside the box; cuMotion then fails at trajopt with UNKNOWN_STATUS. Giving cuMotion a tool0 pose goal lets it choose the configuration against its own world. The approach demo's 170° rewind guard is re-applied to every returned trajectory.

8Nothing existing changed

The map is strictly opt-in. start_cumotion.sh keeps its default behaviour, the tray rig and the approach demo are untouched, and neither reads the map. start_cumotion_map.sh is a sibling script that deliberately reuses the container name, so docker itself refuses to run both planners at once — they would both answer the cumotion/move_group action and MoveIt would talk to whichever won the race.
