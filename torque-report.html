01What it is

For the first time, UR exposes the lowest layer of its control stack to outside code.

Historically UR cobots accepted position and velocity targets (URScript servoj/speedj), with force behavior only through the built-in force_mode black box. Direct Torque Control lets an external program command the current/torque of every joint motor directly at 500 Hz — the layer where impedance control, learned policies, and compliant contact skills actually live. UR positions it squarely at research and AI: NVIDIA Robotics used a beta to demonstrate sim-to-real transfer on a gear-assembly task — training a policy on a simulated UR and running the same torque-level policy on the physical arm.

Enables

True impedance control

Programmable stiffness/damping per joint — the arm behaves like a tunable spring, not a position machine.

Enables

Contact-rich skills

Assembly, polishing, sanding, screwdriving — tasks where regulating force beats tracking position.

Enables

Sim-to-real for RL policies

Torque is the native action space of most learned manipulation policies; no position-controller shim in between.

02Does our robot get it?

Verdict for the lab's UR10

No. Our arm is a CB3 running PolyScope 3.15.8 — the CB3 line is feature-frozen on the 3.x branch. Direct Torque Control requires PolyScope 5.23.0+ (e-Series) or PolyScope X 10.10.0+ (new UR Series). No firmware update can bridge that; it's a controller-generation boundary. Our CB3 also runs its external interfaces at 125 Hz — the torque loop is spec'd at 500 Hz on the newer controllers.

What the CB3 can still do compliantly: URScript force_mode (Cartesian force control in the robot's own controller, driven from ROS via force_mode_controller + passthrough_trajectory_controller) and freedrive. Force estimates come from joint currents — the CB3 has no wrist F/T sensor — so expect tens-of-newtons accuracy, fine for lead-through and gross compliance, not for fine assembly.

04The ROS 2 story — already in the driver we installed

The 3.8.0 Jazzy driver on this workstation ships the torque-era controllers; they're version-gated by the robot, not the PC.

ControllerRole in torque-based controlOn our CB3
forward_effort_controllerDirect joint-torque commands from ROS (JointGroupEffortController) — the ROS face of Direct Torque Control. You send achievable torques; no trajectory safety net.Loaded, unusable (firmware gate)
friction_model_controllerPublishes the robot's joint friction model so torque commands can compensate friction — essential for accurate low-torque behavior. Landed via PR #1704 in driver 5.0.0, backported to our 3.8.0.Active (harmless; feeds nothing)
force_mode_controllerWraps URScript force_mode — Cartesian force via the robot's own controller. The pre-torque-era compliance path.Works (CB3 has force_mode)
tool_contact_controllerContact detection during motion: stops and retracts on tool touch.Loaded

Raw C++ loop shape from UR's own example (ur_client_library):

// robot paces the loop via blocking RTDE read; you answer with torques
// requires PolyScope >= 5.23.0 / 10.10.0 — errors out otherwise
data = driver->getDataPackage();                       // read joint state @500 Hz
tau  = policy(q, qd);                                  // your controller / learned policy
driver->writeJointCommand(tau, comm::ControlMode::MODE_TORQUE, timeout);

05What this means for Aile

Now

CB3 stays position-based

Everything we commissioned (trajectory control, HIL bridge, RViz mirror) is unaffected — torque control changes nothing for the current arm.

If needed

Compliance on CB3

Use force_mode_controller for contact tasks — coarse but real, and already installed.

Upgrade path

e-Series or UR Series

A UR10e/UR15 on PolyScope 5.23+/X 10.10+ unlocks the 500 Hz torque loop with the same driver stack and repo we already run — only ur_type and the calibration file change.

Strategic

Fits our Isaac direction

UR's own launch showcase is NVIDIA sim-to-real (gear assembly). Torque-level policies trained in Isaac transferring to a UR Series arm is exactly the lane our HIL work points at.
