# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Recurring operational commands, health checks, and recovery procedures: `RUNBOOK.md` (authoritative).
- Camera bring-up sharp edges (serial_no YAML trap, orphaned nodes, stale ros2 daemon, torchvision cu130, D415 RGB-interface USB fault): `cams/README.md` "Traps".
- The wrist D435i is mounted upside down. `/wrist/color_upright/*` (+ frame `wrist_color_upright_optical_frame`) is the stream the hand-eye calibration and the cell map consume; `/wrist/color/*` is the untouched driver output. Never pair an image from one with the CameraInfo/frame of the other — `cams/README.md` "Wrist camera is mounted upside down".
- Everything runs on ROS_DOMAIN_ID=0 with `FASTDDS_BUILTIN_TRANSPORTS=UDPv4`; the `shelfbot_ros` container bakes domain 42, so override per `docker exec -e`.
- Killing a `ros2 launch` can orphan its child nodes (they reparent to user init and keep publishing — including static TFs). `pgrep -af <node>` before relaunching anything camera- or TF-related.
- MoveIt pose-goal planning here can sample distant IK configurations (observed: +405° shoulder rewind for a 0.6 m translation). For predictable motion use seeded `/compute_ik` + a joint-space goal (Pilz PTP) and a per-joint delta guard — see `cams/approach/approach_demo.py`.
- Never execute motion on the real arm from an agent session unless the task explicitly authorizes it; plan-only (`plan_only=True` on `/move_action`) is always safe.
- Planning from the park pose (where the arm rests) was blocked by ONE stray weight-1 mid-air voxel in `cell-2026-09-04-cleaned.nvblx` (at base_link `[-0.670,0.130,0.250]`, not real geometry): it was the only occupied voxel inside park's 4 cm buffer, so cuMotion refused every plan starting from park. Corrected map `~/ur10/cumotion/maps/parkpose-fix-cell-2026-09-04-despeck.nvblx` removes exactly that one voxel (park clearance −0.12 → +3.23 cm). NOT live — its `parkpose-*` name sits outside the loader's `cell-*.nvblx` auto-pick, so it is inert until the captain names it to `start_cumotion_map.sh` (RUNBOOK §10). Defect, exact regen command, before/after clearance and one-voxel proof: `data/planner-map-fix-v1/decision.md`.
- Real joint limits come from a captain freedrive hand-sweep, re-measure when the line is re-routed or the arm re-parked: `cumotion/measured_joint_limits.yaml`, where 3 joints carry a captain-declared bound (shoulder_lift at both ends; elbow and wrist_2 floors only, their ceilings kept as measured), and the other 3 (shoulder_pan, wrist_1, wrist_3) are purely hand-swept. Tools: `cams/cellmap/tools/record_joint_limits.py` (`--merge` re-sweep, `--declare` widen-by-decision) and `cumotion/make_limited_urdf.py --frozen --keep-world-collision` (full world collision on a cleaned map) — RUNBOOK §10 "Measuring / declaring real joint limits". Every executed plan must pass `execute_plan.py --limits <that file>`; the executable tag1→shelf demo + its command is `data/cell-clean-approach-v1/captain-execute-note.md`.
- The collision-FORCE threshold lives in two places, only one repo-settable (CB3, no wrist F/T sensor — force is estimated from joint currents, ~152 N clean-motion swing, so it is a coarse signal): the safety-rated protective-stop **Force limit is teach-pendant only** (`Installation → Safety → Safety Limits → Force`, N, CB3 floor 100 N) and cannot be set from ROS/repo; the only repo-settable force threshold is the ROS-side gross-contact backstop in `cumotion/collision_force_limits.yaml` (`ros_contact_force_backstop_n`, consumed by `loop_tags.py` via `cams/cellmap/tools/collision_force.py`). Tracking error, not force, is the effective ROS-side contact guard on CB3 — do not lower `--max-track-rad` (already at its nuisance floor). Rationale, pendant procedure, payload cross-check and one-step revert: `data/collision-force-v1/decision.md`.

- Camera-based human detection/tracking + safety-state layer lives in `cams/human_safety/` (stage 1: perception only, **publishes but never touches the robot**). Pure decision logic (geometry, tracker, `SafetyEvaluator`) is ROS/torch/GPU-free and offline-unit-tested; ROS nodes are thin shells. It runs on isolated `ROS_DOMAIN_ID=77` (+`FASTDDS_BUILTIN_TRANSPORTS=UDPv4`) — the one task that may open the cameras — via `cams/human_safety/run_live.sh` (brings up cameras + graph + viewer + a replay recording, stops by PID, releases the cameras). Torch is user-scoped in `~/venvs/human-safety` (detector nodes only; fusion/viz use system python; images decoded without cv_bridge). State is a versioned JSON schema on `std_msgs/String` `/human_safety/state` (no custom .msg — repo isn't colcon-built), fails toward STOP. **Reality it's built for:** all three cameras are presence-only until they have a `base_link` pose (wrist FK needs `/joint_states` = driver up; both D415s need a fixed-camera AprilTag calibration a SEPARATE task owns). This layer is explicitly **NOT a certified safety function**. Robot-side gate design + provisional zone/latency figures: `/home/manishsaini/firstmate/data/human-safety-s1/report.md`. Full detail: `cams/human_safety/README.md`.
