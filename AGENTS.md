- The nvblox **dynamic layer** feeding cuMotion (SIM-ONLY, plan-only) lives in `cams/cellmap/dynamic/`, distinct from the cell's static snapshot (`nvblox_cell.yaml`/`live.launch.py`, decay OFF). On the planner image (nvblox_ros **4.4.0**), `mapping_type: dynamic` is the mode whose obstacles reach cuMotion: `get_esdf_and_gradient` returns a **dense 3D single-channel** ESDF (`layout.dim=[x,y,z]`, `len(data)=x*y*z` — do NOT treat the last dim as gradient channels; that bug reads one z-layer and looks like a "2D slice / frozen map"), and in `dynamic` mode it gains appearing/moving obstacles and decays them out (~0.5–1 s appear/clear; plan ~0.16–0.2 s; ESDF call ~10 ms; peak ~1.0–1.1 GB over the voice baseline). The `human_with_static_*` people-seg modes are the WRONG tool: the PeopleSemSegNet model is not in the image (NGC-installer-only) and masked-human voxels are REMOVED from the served ESDF, so cuMotion would ignore people — a person is instead routed as a generic dynamic volume. Principle (enforced by `routing_gate.py`, proved end-to-end through `humangate`): the map is a ROUTING aid, never the stop. Fixed cameras stay refused until calibrated (`extrinsics_guard.py`, same guard as `camera_poses.py`). Runs on `ROS_DOMAIN_ID=85`. Self-asserting proofs in `cams/cellmap/dynamic/proof/`; full detail + measurements: `cams/cellmap/dynamic/README.md`, `data/plan-nvblox-dynamic-v1/decision.md`.
- The cuRobo reactive-MPC planner prototype (option C3 of the human-dynamic-plan-s1 report) lives in `mpc_curobo/` — SIM/EVAL ONLY on `ROS_DOMAIN_ID=84`. Licence: cuRobo **V2 (v0.8.0) is Apache-2.0 and DOES expose MPC** — v1 (`v0.7.x`, where the MPC docs point) is NVIDIA non-commercial; the prototype pins v0.8.0 and is kept out of any shipped dependency pending the owner call in `~/firstmate/data/plan-mpc-curobo-v1/decision.md`. It has its OWN CUDA-devel + ROS 2 Humble + UR-driver + cuRobo image `fm-plan-mpc-curobo-v1` (`mpc_curobo/Dockerfile`, ~10 min build; the host has no nvcc); the cell UR10 is fed to cuRobo via `mpc_curobo/robot/ur10_cell_curobo.yml`, generated from `cumotion/ur10_measured.{urdf,xrdf}` + `measured_joint_limits.yaml` (cuRobo reads the captain windows straight from the URDF `<limit>` tags). The gate-mediated ROS bridge (`mpc_curobo/ros_bridge/`, reuses `humangate` + the unchanged `humangate_driver/arming_interlock.py`) streams to the driver's **`forward_position_controller`, which HOLDS its last setpoint when the command STREAM starves WHILE THE DRIVER IS ALIVE → the arm ends stopped** (verified by killing the bridge mid-motion; answers report RD-3 for the stream-death case). This is a LAYERED story, not a bridge-alone guarantee: if the driver itself dies, what stops the arm is a separate layer (the robot external-control program ending); and `forward_velocity_controller` would coast — do not use it for streamed control. Sharp edges (ASCII-only cuRobo YAML loader; wrap-aware revolute-joint guard for the unwrapped `wrist_1` window; re-assert the MPC goal every tick; multi-threaded executor so the solve doesn't starve the gate) and measured numbers (~55-59 Hz, ~17 ms, ~215 MiB) are in `mpc_curobo/README.md` and `~/firstmate/data/plan-mpc-curobo-v1/report.md`.
