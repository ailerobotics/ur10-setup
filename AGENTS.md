- Isaac Sim test harness for the `cams/human_safety` graph lives in `sim/isaac_human/` (SIM-ONLY, `ROS_DOMAIN_ID=88`, `ROS_LOCALHOST_ONLY=1`, always under `flock ~/.cache/fleet-gpu.lock`). It runs the UNCHANGED detector+fusion graph against Isaac-simulated RGB-D cameras watching a rendered person walk a scripted path around a UR10 stand-in, with the simulator's TRUE person position as ground truth. The `safety:` block of `params/human_safety.sim.yaml` is a verbatim copy of the production config (a test enforces no threshold drift); `params/camera_poses.sim.yaml` is GENERATED from `cell_layout.py` by `gen_sim_config.py` (inline base_link←optical TFs, so the detector's TF is exactly the pose Isaac renders from). Two sharp edges: cameras MUST publish with `useSystemTime=True` or the detector's `latency = now − image_stamp` explodes and pins STOP; and Isaac's RTX renderer + Keypoint-R-CNN share the one 12 GB card, so **2+ cameras push img→state latency past the 0.70 s reaction budget (permanent fail-safe STOP)** — the default run uses a SINGLE camera (`run_session.sh` warns if more are requested) + `--sim-hz` throttle; a 2-camera run is only for the per-camera accuracy split. Isaac uses its BUNDLED ROS 2 (`isaac_env.sh`), the graph uses system `/opt/ros/jazzy`; they meet over DDS. Boot smoke test first (`run_boot_smoke.sh`); full run `run_session.sh`; offline analysis `analyze.py`+`diagnose.py`+`make_report.py`. **Detection-accuracy finding this test surfaced, now FIXED:** the original run (PR #22) localised the sim person 100% of in-view frames but the published STOP-ring distance over-stated clearance by **+0.4–0.9 m in the UNSAFE direction** (person reported FARTHER than truth → a missed STOP with the nearest true body point already ~0.9 m INSIDE the 2.0 m ring), because the zone was sized from the depth-median body **centre** (`t.position`), which the clean sim floor drags behind the person, while the accurate `t.nearest_point` was carried but unused. Fixed in the production layer: the zone now reacts to the nearest credible body point (speckle-filtered, never larger than the centre) and `geometry.lift_depth` takes the centre from the foreground depth cluster only, so background floor no longer drags it back — no missed STOP on the healthy-latency replay, no new zone chatter on the committed replay regression (a ~0.19 m residual over-statement remains in the nearest-point estimate; owner-decision follow-ups in the report). Invariant guarded by `sim/isaac_human/tests/test_after_run_replay.py` (reverting the nearest-point logic fails it). The harness keeps the teleported T-pose on purpose — it maximises the centre bias the fix must overcome; a body-filled natural pose needs `omni.anim.people`, not built. Before/after + the fix: `data/human-safety-nearest-point-fix-v1/report.md`; original FAIL record: `sim/isaac_human/README.md`, `data/human-detect-isaac-sim-v1/report.md`.

- The nvblox **dynamic layer** feeding cuMotion (SIM-ONLY, plan-only) lives in `cams/cellmap/dynamic/`, distinct from the cell's static snapshot (`nvblox_cell.yaml`/`live.launch.py`, decay OFF). On the planner image (nvblox_ros **4.4.0**), `mapping_type: dynamic` is the mode whose obstacles reach cuMotion: `get_esdf_and_gradient` returns a **dense 3D single-channel** ESDF (`layout.dim=[x,y,z]`, `len(data)=x*y*z` — do NOT treat the last dim as gradient channels; that bug reads one z-layer and looks like a "2D slice / frozen map"), and in `dynamic` mode it gains appearing/moving obstacles and decays them out (~0.5–1 s appear/clear; plan ~0.16–0.2 s; ESDF call ~10 ms; peak ~1.0–1.1 GB over the voice baseline). The `human_with_static_*` people-seg modes are the WRONG tool: the PeopleSemSegNet model is not in the image (NGC-installer-only) and masked-human voxels are REMOVED from the served ESDF, so cuMotion would ignore people — a person is instead routed as a generic dynamic volume. Principle (enforced by `routing_gate.py`, proved end-to-end through `humangate`): the map is a ROUTING aid, never the stop. Fixed cameras stay refused until calibrated (`extrinsics_guard.py`, same guard as `camera_poses.py`). Runs on `ROS_DOMAIN_ID=85`. Self-asserting proofs in `cams/cellmap/dynamic/proof/`; full detail + measurements: `cams/cellmap/dynamic/README.md`, `data/plan-nvblox-dynamic-v1/decision.md`.

Licence: cuRobo **V2 (v0.8.0) is Apache-2.0 and DOES expose MPC** — v1 (`v0.7.x`, where the MPC docs point) is NVIDIA non-commercial; the prototype pins v0.8.0 and is kept out of any shipped dependency pending the owner call in `~/firstmate/data/plan-mpc-curobo-v1/decision.md`. It has its OWN CUDA-devel + ROS 2 Humble + UR-driver + cuRobo image `fm-plan-mpc-curobo-v1` (`mpc_curobo/Dockerfile`, ~10 min build; the host has no nvcc); the cell UR10 is fed to cuRobo via `mpc_curobo/robot/ur10_cell_curobo.yml`, generated from `cumotion/ur10_measured.{urdf,xrdf}` + `measured_joint_limits.yaml` (cuRobo reads the captain windows straight from the URDF `<limit>` tags). The gate-mediated ROS bridge (`mpc_curobo/ros_bridge/`, reuses `humangate` + the unchanged `humangate_driver/arming_interlock.py`) streams to the driver's **`forward_position_controller`, which HOLDS its last setpoint when the command STREAM starves WHILE THE DRIVER IS ALIVE → the arm ends stopped** (verified by killing the bridge mid-motion; answers report RD-3 for the stream-death case). This is a LAYERED story, not a bridge-alone guarantee: if the driver itself dies, what stops the arm is a separate layer (the robot external-control program ending); and `forward_velocity_controller` would coast — do not use it for streamed control. Sharp edges (ASCII-only cuRobo YAML loader; wrap-aware revolute-joint guard for the unwrapped `wrist_1` window; re-assert the MPC goal every tick; multi-threaded executor so the solve doesn't starve the gate) and measured numbers (~55-59 Hz, ~17 ms, ~215 MiB) are in `mpc_curobo/README.md` and `~/firstmate/data/plan-mpc-curobo-v1/report.md`.
